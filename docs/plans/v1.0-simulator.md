# v1.0 Interactive simulator plans

Build the model first, then rendering, controls, learning scenarios, accessibility, and publication. All six issues describe a browser-only educational tool. Keep the Go service and real infrastructure independent of this workspace. Dependencies and the shared completion workflow are in the [plan index](README.md).

The [detailed simulator design](simulator-design.md) expands these phases using PGSimCity and other primary references. The user selected a light isometric campus within the PixiJS 2D scope, project behavior with clearly labeled teaching values, and direct entry into a working sandbox with a short optional introduction. Changing settings and seeing the consequences remains the priority. The design distinguishes repository contracts from synthetic capacities and explicitly omitted mechanisms.

Further choices confirmed on 5 November 2026: traffic controls stay visible, buildings expose their own settings with advanced options tucked away, and the first finished release includes one saved baseline with a matched-workload before/after summary. The first playable preview focuses on scaling and backend failure/retry; draining and the Redis bottleneck follow, with all four experiments still required for completion.

## Issue 15 Deterministic cluster model

[Issue 15](https://github.com/kajuyerim/docker-based-multiserver-system/issues/15). **Entry:** v0.5 is complete. **Prepare:** fixed-step simulation, seeded randomness, queues, and the existing root handler's counter order. **Targets:** `simulator/package.json`, lockfile, `simulator/src/model/`, model tests, and an initial `simulator/MODEL.md`.

1. **Define the model and workspace.** Add Vite, TypeScript, and a small unit-test runner. Specify typed commands, logical request/attempt/Redis-operation IDs, integer time, stable event ordering, seeded randomness, and immutable snapshots. Separate backend CPU work from sleeping/Redis waits and in-flight occupancy. Label finite admission limits as model assumptions. Separate Redis execution cost from transport delay. Start with proposed bounds of 1–8 replicas; validate final limits in issue 16. Check the core has no DOM or PixiJS imports.
2. **Implement deterministic execution.** Build arrivals, round-robin routing, backend CPU queues, serial Redis work, and responses. Use fixed outer ticks with precise event times inside each tick so short Redis operations are not rounded into false bottlenecks. Commands enter at a named boundary; wall time only controls how many steps run. Pause, resume, single-step, speed, and reset must preserve the same outcome for the same seed and commands. Test replay equality and snapshot immutability.
3. **Add failure and state semantics.** Model process health separately from proxy knowledge, stop/restart, coordinated drain, eligible retries, Redis unavailability, and saturation. Local count advances before INCR; successful roots also issue PUBLISH; publish failure can still yield HTTP 200. The configured proxy does not retry Redis-error HTTP 500. `/slow` sleeps without Redis/counter work. Explicitly omit internal Redis-client retries initially. Restart resets local process state while the chosen Redis-unavailability mode retains shared state. Define queued, committed, and in-flight outcomes for every transition.
4. **Prove the mechanisms.** Test distribution, overload, queue overflow, retries exhausted, no healthy backend, graceful drain, restart counters, and Redis as the eventual scaling bottleneck. Assert request conservation across terminal and in-flight states, finite queues, and exact same-seed replay across pause/speed changes. Include a different-seed case that can actually differ.

**Exit evidence:** repeatable model tests and a documented snapshot/command contract that issues 16–18 can consume. The user selected a labeled capacity sandbox omitting the real per-client rate limiter. Do not present model rates as measured stack capacity. Use a commit scope such as `feat(simulator)` or `test(simulator)` per phase.

## Issue 16 Interactive 2D visualization

[Issue 16](https://github.com/kajuyerim/docker-based-multiserver-system/issues/16). **Entry:** issue 15. **Prepare:** PixiJS scene structure and the snapshot contract. **Targets:** `simulator/src/view/`, layout code, a DOM inspector, and visual fixtures.

1. **Create the topology view.** Render the client, NGINX, replicas, and Redis as a light isometric campus using original shapes and literal labels. Keep paths and queues visible together without camera navigation. Establish icon/text/color states for idle, busy, saturated, failed, and draining. Keep a stable component ID shared with a DOM selection list so keyboard access can be completed in issue 19.
2. **Render request lifecycles.** Consume model events/snapshots for arrival, routing, queueing, processing, Redis access, response, retry, and failure. Interpolate between known simulation states for smooth drawing; animation timing must never decide routing, completion, or counters. Verify a scripted request against the model's complete event sequence.
3. **Add inspection.** Selecting a component shows its role, state, queues, capacity, and relevant metrics. Use one selection state for the canvas and DOM inspector. Handle removal or restart of the selected component without stale references. Freeze fixture snapshots to catch accidental mutation by the renderer.
4. **Bound and measure rendering.** Profile maximum replicas and request activity on a named machine/browser. Reuse graphical objects and cap visible packet markers if necessary, clearly labeling visual sampling while preserving all modeled requests and metrics. Set the interaction/frame-time acceptance budget before the final run; check sustained operation for memory growth and accurate overload states.

**Exit evidence:** screenshots of all semantic states, a lifecycle walkthrough, and a performance record with supported limits. Avoid elaborate game art or shader work until the view communicates the tested model clearly.

## Issue 17 Operational controls

[Issue 17](https://github.com/kajuyerim/docker-based-multiserver-system/issues/17). **Entry:** issues 15–16. **Prepare:** the distinction between immediate failure and graceful drain. **Targets:** `simulator/src/controls/`, model command validation, and interaction tests.

1. **Define the command behavior.** Document legal bounds and units for replica count, per-replica CPU capacity, offered request rate, slow-request percentage, Redis processing time, Redis network delay, and playback speed. Specify effects on current versus future work. Define stop, restart, coordinated drain, and removal separately. Support total outage deliberately and handle attempts to remove a replica already draining.
2. **Connect accessible controls.** Keep native traffic controls visible and expose other settings through the selected building's inspector, with advanced options in a disclosure. Include Redis online/offline, NGINX retry on/off, and pause/reset. Route changes through the model command queue; inspectors and controls cannot write snapshots. Show current values, units, and reasons for disabled actions. Keep controls operable while paused and ensure keyboard selection opens the same settings.
3. **Make changes reproducible.** Preserve a seed and tick-indexed action log for replay tests. Define whether reset restores the scenario defaults or the current configuration; provide clear labels. Test fixed command sequences for overload, scale-out, Redis failure/recovery, retry toggling, and drain/restart.
4. **Check the complete interaction.** Exercise minimum/maximum and invalid inputs, repeated clicks, removing a selected replica, changes during pause, and reset with pending work. Assert effects on queues, latency, throughput, errors, and counters instead of merely checking that a slider moved.

**Exit evidence:** an interaction matrix linking every control to its model command, expected visible effect, and test. Keep the controls focused on this issue; scenario scripting belongs to issue 18.

## Issue 18 Metrics and guided scenarios

[Issue 18](https://github.com/kajuyerim/docker-based-multiserver-system/issues/18). **Entry:** issues 15–17. **Prepare:** offered versus completed throughput, error denominators, and percentiles. **Targets:** `simulator/src/metrics/`, `simulator/src/scenarios/`, metric panels, and scenario fixtures.

1. **Define metric contracts.** Use simulated time and a bounded history. Specify throughput and success/error denominators, completed-request average and p95 latency, queue depth, per-replica distribution, local/global counters, and Redis busy-time utilization. Separate logical requests from backend attempts so retries do not inflate client throughput. Define empty-window, paused, reset, and pending-request behavior; add known-value percentile tests.
2. **Build readable panels and comparison.** Derive panels and charts from the same snapshots as the canvas. Label units/windows and separate offered load from completed work. Show pending count and oldest pending age alongside completed-request latency. Save one baseline and compare a sequential candidate run using the same workload seed, offered request stream, initial-state convention, and observation window. Show changed settings, sample counts, before/after values, and explicit mismatch/no-data states. Test that charts, inspectors, and summaries agree.
3. **Author four experiments.** Add scaling under load, backend outage with retry, graceful drain, and a Redis bottleneck. Each uses a seed, setup, observation prompt, metric-based completion condition, and reset. Scaling should improve a backend-limited workload until Redis becomes limiting; drain should finish admitted work while new arrivals use other healthy replicas.
4. **Verify learning outcomes.** Replay every scenario headlessly and test expected outcomes and a negative case that must not complete. Test identical-run comparison, incomplete/mismatched windows or workloads, changed seeds/versions, and zero/no-data values. Add browser checks for starting, interrupting, switching, resetting, and explicitly replacing/clearing the saved baseline. Bound stored samples so a long session does not grow indefinitely.

**Exit evidence:** four reproducible scenario transcripts, a verified saved-baseline comparison, and metric definitions in `MODEL.md`. Scenario claims must describe this model; the project's k6 measurements remain separately labeled real-stack evidence.

## Issue 19 Accessibility and model boundaries

[Issue 19](https://github.com/kajuyerim/docker-based-multiserver-system/issues/19). **Entry:** interaction design from issues 16–18 is stable. Accessibility foundations should already be present. **Prepare:** keyboard focus, reduced motion, and screen-reader output. **Targets:** DOM controls/summary, responsive styles, `simulator/MODEL.md`, and browser checks.

1. **Complete the text interface.** Provide keyboard selection and inspection for every component, visible focus, labels, and meaningful status text. Summarize topology, active failures, queues, and headline metrics outside the canvas. Announce important changes at a bounded rate; avoid reading every tick. Restore focus sensibly after removal/reset.
2. **Handle motion and small screens.** Respect reduced-motion preferences and offer a visible control. Replace moving packets with a static state/summary without changing simulation results. Use icons/text alongside color. Check desktop, tablet, and narrow phone layouts for operable controls, readable inspectors, and no essential information hidden behind canvas gestures.
3. **Finish the accuracy document.** Record formulas, units, defaults, bounds, retry/counter semantics, queue policy, Redis model, seeds, and simplifications. Explain omitted network, persistence, Kubernetes, and failure details. Put “educational model” prominently in the UI and explain that it is neither an emulator nor a production monitor. Inventory original assets and any dependency notices.
4. **Audit real use.** Combine automated accessibility checks with a keyboard-only walkthrough, a screen-reader check, reduced motion, zoom, contrast, and the agreed browser/viewport matrix. Verify users can run and understand all scenarios through the text interface. Record specific remaining limitations rather than claiming full compliance from a scanner alone.

**Exit evidence:** completed usability checklist, responsive screenshots, asset provenance, and the model-accuracy document. No third-party game branding or borrowed character assets.

## Issue 20 GitHub Pages publication

[Issue 20](https://github.com/kajuyerim/docker-based-multiserver-system/issues/20). **Entry:** issues 15–19. **Prepare:** static asset base paths and the repository's Pages eligibility. **Targets:** `simulator/vite.config.ts`, a dedicated Pages workflow, deployment notes, and the README.

1. **Resolve the publication route.** Check the actual repository/account settings against [GitHub Pages availability](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). Keep visibility changes and license decisions explicit. Review only the intended public export, including bundled assets and relevant history; never upload the repository root as the site artifact.
2. **Build under the project path.** Configure `/docker-based-multiserver-system/` for the existing repository destination, or the selected destination's actual path. Prefer a single page or hash navigation unless deep-link hosting has been deliberately solved. Test the production output under that prefix, including assets, reload, reset, and reduced motion. [Vite deployment guidance](https://vite.dev/guide/static-deploy.html).
3. **Add isolated delivery.** PRs run dependency installation from the lockfile, type checks, model/scenario tests, and a production build. A trusted deployment job uses the official Pages artifact/deploy actions with only required job permissions, pinned revisions, and deployment concurrency. Upload only `simulator/dist`; no backend, runtime secret, or visitor Docker connection is required.
4. **Verify the live artifact.** After the agreed publication action, check the actual URL in a fresh browser, direct loading, paths, keyboard use, mobile layout, and network requests. Run a scenario with the local stack stopped. Add the verified live link, screenshot, concise explanation, and deployment/rollback instructions to README.

**Exit evidence:** successful build/deployment run and live-browser checks. If hosting eligibility is unresolved, preserve the tested static bundle and mark deployment pending; do not invent a live URL or call the issue complete.
