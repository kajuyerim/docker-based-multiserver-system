# v1.2 Local Kubernetes platform plans

Extend the opt-in lab while retaining the simple Compose and kind paths. The sequence is Flux, isolation, secret lifecycle, then telemetry. Shared experiment and completion requirements are in the [plan index](README.md).

## Issue 34 Flux GitOps delivery

[Issue 34](https://github.com/kajuyerim/docker-based-multiserver-system/issues/34). **Entry:** issues 32–33. **Prepare:** desired state, reconciliation, HelmRelease health, and Git revert. **Targets:** `gitops/`, promotion verification, and `docs/gitops.md`.

1. **Define sources and ownership.** Reuse the existing chart through Flux, with separate dev/staging namespaces, Secrets, Redis services, and volumes. Use a repository-scoped read-only deploy credential or a private local Git service reachable by Flux; do not expose it anonymously on the LAN. Bootstrap controllers remain OpenTofu-owned. Allow staged environment startup to fit the resource budget. Document why one Flux installation is sufficient.
2. **Reconcile a verified release.** Pin chart/source and image identity. Use issue 32 verification before accepting promotion: check signer, subject, revision, and artifact hashes, then review the configuration diff. Promote the same image digest from dev to staging with no rebuild. Specify dependencies, readiness/health checks, retry intervals, pruning, and deliberate PVC retention. Keep credentials outside Git until issue 36 adds encrypted configuration.
3. **Prove drift repair without ownership conflicts.** Enable the selected Flux Helm drift-correction behavior explicitly; a Git source alone does not prove correction of a manual Deployment patch. Exclude HPA-controlled replica fields and test that desired/ready replica changes survive reconciliation. Demonstrate correction of a harmless managed configuration drift. Test retention through reconciliation and a controlled removal/uninstall in an owned disposable environment. [Flux Helm drift detection](https://fluxcd.io/flux/components/helm/helmreleases/#drift-detection).
4. **Exercise failed deployment and rollback.** Apply an invalid image or deliberately unhealthy revision through a lab Git branch. Capture reconciliation status and client outcomes, then revert the configuration commit and require healthy service at the previous digest. Verify dev/staging state isolation and record the desired Git commit, actual image ID, rollout, and rollback. Explain any difference between automated Helm remediation and the operator's Git revert.

**Exit evidence:** promotion, drift repair, HPA coexistence, bad-rollout recovery, and data-retention transcripts. Proposed commits use `feat(gitops)`. Decide the Git source and recovery/pruning policy before phase 1; never equate a healthy controller with a healthy application.

## Issue 35 Network isolation and workload security

[Issue 35](https://github.com/kajuyerim/docker-based-multiserver-system/issues/35). **Entry:** issues 33–34. **Prepare:** namespace/pod selectors, ingress/egress policy, service accounts, and Pod Security Admission. **Targets:** the lab CNI bootstrap, Helm security settings, GitOps policies, negative fixtures, and a connectivity runner.

1. **Prove CNI support first.** Select one pinned NetworkPolicy-capable CNI after checking kind, Kubernetes, Apple Silicon runtime/kernel, and resource compatibility. Have OpenTofu own its installation under the ownership table. Configure the lab network at cluster creation and document any required recreation; do not hot-swap the user's existing environment. Before wider changes, prove a tiny allow/deny example. Policy YAML without enforcement does nothing. [Kubernetes prerequisites](https://kubernetes.io/docs/concepts/services-networking/network-policies/#prerequisites).
2. **Implement the traffic matrix.** Default-deny application namespace ingress and egress; add exact namespace/pod/port rules for ingress controller → NGINX → app → Redis, replication, DNS, and specified telemetry. Model both endpoints' policy needs, including DNS TCP/UDP. Prepare bounded labeled telemetry peers now; actual integrations are issue 37's responsibility. Keep Redis and management UIs away from public host exposure.
3. **Apply minimum workload privileges.** Use scoped service accounts/RBAC and disable API-token automount for workloads that do not need it. Set appropriate namespace admission and non-root, seccomp, capability, privilege-escalation, and filesystem controls. Test real NGINX/Redis images for writable runtime paths and port requirements; use narrow writable mounts or a justified minimal exception instead of weakening the entire namespace. Keep probes, startup, persistence, and graceful shutdown working.
4. **Validate behavior and rejection.** Add schema/policy checks and synthetic fixtures that reject privileged workloads and public Redis exposure. Test allowed API, WebSocket, replication, and DNS traffic; denied cross-namespace/app-bypass Redis access; and recovery after test peers are removed. Check management binds/authentication and retain an allowed/denied matrix with timeouts. Run regression checks on default chart output.

**Exit evidence:** actual packet/connectivity results, security-policy rejection, and an ownership/traffic diagram. Single-host kind isolation is a lab demonstration, not tenant-grade security. Future Sentinel and monitoring changes must extend the same matrix and tests. Use `feat(security)` phase commits.

## Issue 36 Secret and certificate rotation

[Issue 36](https://github.com/kajuyerim/docker-based-multiserver-system/issues/36). **Entry:** issues 34–35. **Prepare:** encryption recipients, bootstrap trust, certificate hostname/chain validation, and rolling credential changes. **Targets:** SOPS configuration, encrypted lab manifests, local bootstrap/rotation helpers, and a recovery guide.

1. **Establish encryption and recovery.** Generate each user's own age key and credentials. Store private keys and their backup outside Git, container layers, OpenTofu state, and ordinary logs. Bootstrap the decryption Secret directly into the lab, then configure Flux decryption and commit ciphertext/templates only. Keep read-only Git credentials separately scoped with their own rotation instructions. Document fresh-user setup and recovery after cluster recreation. [Flux SOPS and age workflow](https://fluxcd.io/flux/guides/mozilla-sops/).
2. **Rehearse application-token rotation.** The current application accepts one token and reads it at process startup; a Secret edit alone does not rotate running pods. Define the transition and acceptable interruption before execution. Coordinate new token, backend rollout, NGINX/probe clients, tests, and any current monitoring clients. Prefer an honest measured short transition over adding a second credential mode without need. Verify new credentials across every pod and the front door, and rejection of the old token after completion. Document the mounted-secret/reload contract issue 37 will consume.
3. **Rehearse local TLS renewal.** Use a local CA with an explicit CA-file trust path by default, keeping system trust unchanged. Issue a certificate with the actual lab hostname, distribute its encrypted Secret, renew/replace it, and verify the served certificate and chain without insecure TLS bypass. Test an untrusted CA, wrong hostname, and the replaced certificate's disappearance. Record interruption, if any.
4. **Prove failure and key recovery.** Exercise wrong/missing decryption key, recover from the backup, and rotate to a new age recipient with re-encryption and a fresh-cluster check. Explain that removing a recipient cannot revoke old ciphertext already copied. Restore safe application access after each drill and inspect diagnostics/screenshots for plaintext disclosure.

**Exit evidence:** successful token and certificate rotation, old-token rejection, key-loss recovery, and sanitized transcripts. Decide key backup location and interruption budget before phase 1. System-wide CA trust changes require the user's explicit choice. Use `feat(secrets)` phase commits.

## Issue 37 Kubernetes observability

[Issue 37](https://github.com/kajuyerim/docker-based-multiserver-system/issues/37). **Entry:** issues 34–36. **Prepare:** direct pod discovery, metric aggregation, trace parentage, and telemetry failure behavior. **Targets:** opt-in GitOps telemetry, adapted `monitoring/` configuration, Helm tracing settings, and focused Kubernetes telemetry checks.

1. **Choose a bounded profile.** Reuse Prometheus, Grafana, and the existing OpenTelemetry/Jaeger approach with pinned components, explicit CPU/memory/storage limits, bounded retention, and a lightweight profile. Keep configuration under Flux ownership and UIs loopback-only or authenticated. Add only the platform/Redis signal collectors needed to expose pod readiness/restarts, deployment/HPA state, replication/role, and component health. Extend scoped RBAC and the traffic matrix accordingly.
2. **Discover every replica.** Scrape each app pod directly using authenticated discovery, including changing pod identities after scaling and rollouts. Reuse metric names and dashboard definitions with minimal label/query adaptations. Do not sum the identical shared-counter gauge across replicas; choose an explicit representative/aggregation interpretation. Verify credential rotation and absence of stale targets after termination.
3. **Bring the trace chain to Kubernetes.** Prefer the already-working Compose NGINX instrumentation approach if compatible with the pinned image. Verify the ingress/NGINX → Go → Redis parent-child chain, not merely a common request ID. Test propagation through the extra ingress hop and document where its own span exists or does not. Preserve authentication and query/Redis-statement redaction at collection/storage; inspect an exported trace with synthetic data.
4. **Exercise discovery and outages.** Scale, roll out, stop the collector, and separately interrupt monitoring while continuously probing the API. Verify requests remain available, telemetry reconnects without unrelated app restarts, and new pods appear correctly. Measure idle/loaded CPU, memory, disk, and storage growth for both profiles. Adapt existing metrics/tracing assertions into focused local integration checks.

**Exit evidence:** changing-pod dashboard, actual correlated trace, discovery checks, outage/recovery results, and measured overhead. Durable tracing and hosted services are unnecessary. Use `feat(observability)` phase commits and retain the Compose demo.
