# v1.3 Reliability and disaster recovery plans

Use the completed local platform to measure specific behavior. The suggested sequence is 39, 38, 41, the first version of 42, then optional Sentinel work in 40 and an evidence update to 42. This puts alerting before disruption drills and useful backups before a more complex failover topology. Follow the [shared evidence requirements](README.md#evidence-to-collect-as-you-work).

## Issue 38 Autoscaling and disruption tests

[Issue 38](https://github.com/kajuyerim/docker-based-multiserver-system/issues/38). **Entry:** issues 34–35 and 37; issue 39 is useful but not a required dependency. **Prepare:** CPU utilization relative to requests, HPA stabilization, placement, and voluntary disruptions. **Targets:** lab topology and chart values, focused load/drain runners, and an HPA timeline report.

1. **Make the drain topology credible.** Use the measured multi-worker profile, distribute app replicas, and add appropriate PodDisruptionBudgets and topology constraints. Provide at least two application NGINX replicas on separate eligible workers for the selected drain. Identify remaining single points in ingress, Redis storage, control plane, and host hardware. Predeclare the selected drain node and stateful exclusions; a stateless-worker drain must not imply node-local Redis volumes can relocate. Check that multiple NGINX pods do not silently multiply the intended public rate limit; settle and test its placement/semantics before proceeding.
2. **Calibrate real CPU pressure.** Keep the public root limiter intact. Build a bounded workload using legitimate endpoint traffic and inspect CPU, Redis latency, root 429s, and generator saturation. Set and document realistic CPU requests and limits. Demonstrate that the selected signal can rise above the HPA target; do not count sleeping `/slow` calls or a saturated Redis primary as backend CPU load. If the signal is unsuitable, preserve the evidence and agree on the smallest alternative before adding scaling infrastructure. [Kubernetes HPA behavior](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).
3. **Measure scale-out and scale-in.** Record input metrics, desired/ready replicas, scale-out delay, stabilization, scale-in, client errors/latency, and resource use. Confirm new server IDs receive traffic and Flux does not reset replicas. Include a low-load/no-scale control and post-load recovery. Distinguish accepted-only latency from all client outcomes.
4. **Test disruption with fixed gates.** Predeclare workload, duration, success/latency thresholds, sample requirements, and exclusions. Run a voluntary worker drain and a separate rolling update under continuous requests. Fail on threshold breaches or missing measurements. Restore only changed resources, uncordon the targeted node, and verify placement and steady-state health. PDB evidence applies to voluntary disruption, not arbitrary crashes.

**Exit evidence:** raw timestamped HPA/client timelines, source/config digests, no-scale result, and drain/rollout outcomes. A healthy HPA condition alone does not complete the issue. Use `test(scaling)` and narrowly scoped `feat(k8s)` commits.

## Issue 39 Client facing SLOs and local alerts

[Issue 39](https://github.com/kajuyerim/docker-based-multiserver-system/issues/39). **Entry:** issue 37. **Prepare:** service-level indicators, error budgets, burn rates, and missing-data behavior. **Targets:** `docs/slo.md`, Prometheus recording/alert rules and fixtures, local webhook receiver, and four runbooks.

1. **Write the service contract.** Choose availability and latency targets, eligible operations, windows, minimum traffic, and latency thresholds before the drill. Define numerator/denominator and treatment of expected unauthorized calls, accidental auth failures, rate-limit responses, health/metrics traffic, intentional slow requests, and idle WebSockets. Keep the existing five-minute 95% chaos gate distinct from any operating target. Measure client/front-door attempts, including DNS/connect/TLS failures, proxy errors, and deadline timeouts. Use an instrumented local probe/load client; label its coverage as synthetic traffic rather than all users.
2. **Implement rules and delivery.** Export bounded client counters and duration histograms and retain raw request outcomes for reconciliation. Add availability/latency recording rules, appropriate multi-window burn alerts, and separate missing-traffic/target-down signals. Define low-traffic gating rather than treating an empty denominator as 100% success. Route Alertmanager to a local receiver with timestamped, redacted event capture. Keep the alert path local. [SRE alerting guidance](https://sre.google/workbook/alerting-on-slos/).
3. **Prove rule semantics.** Add [promtool rule tests](https://prometheus.io/docs/prometheus/latest/configuration/unit_testing_rules/) for healthy traffic, burst errors, sustained errors, no data, counter resets, and recovery. Check alert labels and timing. Verify receiver firing, grouping, deduplication, and resolved notifications, including receiver/monitoring loss signals. A complete monitoring outage cannot self-deliver its own alert; use an independent local check or document that boundary explicitly.
4. **Use runbooks in a live drill.** Write diagnosis, mitigation, rollback, and verification steps for backend outage, Redis unavailability, bad deployment, and monitoring loss. Execute an owned isolated failure that actually breaches the selected SLI; a single backend stop hidden by retries may correctly produce no availability alert. Capture detection, notification, mitigation, and recovery times. If using accelerated test windows, keep a separately labeled drill configuration and leave operating targets unchanged.

**Exit evidence:** locally firing/resolving alerts, reconciled client measurements, rule tests, an error-budget view, and a runbook actually used. Short drills validate mechanisms, not month-long uptime. Use `feat(alerting)` and `docs(runbooks)` commits; decide numerical SLO targets in phase 1.

## Issue 40 Redis Sentinel stretch lab

[Issue 40](https://github.com/kajuyerim/docker-based-multiserver-system/issues/40). **Entry:** issues 35–37 and 39. Completing backup issue 41 first is recommended, not an added tracker dependency. **Prepare:** elections, quorum versus majority, asynchronous replication, and ambiguous write outcomes. **Targets:** opt-in Helm/GitOps Sentinel topology, Redis client initialization, telemetry/PubSub integration, and a dedicated failure runner.

1. **Specify topology and write policy.** Proposed lab topology: one primary, two replicas, and three Sentinels spread across three workers, quorum two, persistent identities/storage, and writable Sentinel configuration. Verify it fits the measured profile. Define allowed network paths, Redis/Sentinel credentials, election/recovery thresholds, and replica availability/lag requirements for accepting writes. Preserve the default fixed-primary Compose and Kubernetes modes. Document quorum loss and partition expectations before implementation. [Redis Sentinel semantics](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/).
2. **Adapt clients without changing endpoint contracts.** Add opt-in Sentinel discovery for writes and an explicit replica-read selection/fallback policy after promotion. Start from the existing constructors and introduce only interfaces needed by the chosen clients. Keep INCR atomic. Audit NGINX, application, and Redis-client retries together: a timed-out increment may already have committed, and replay can double-count. Ensure metrics, tracing, authenticated connections, and Pub/Sub subscriptions reconnect to the correct roles. Test startup, shutdown, and default-mode regressions.
3. **Exercise promotion and rejoin.** Under a timestamped client workload, stop the primary, observe detection/election/promotion, and require resumed writes within the predeclared threshold without restarting the application. Verify eventual reads, new-primary metrics, authenticated Pub/Sub, and the old primary returning as a replica. Repeat the drill with fresh run-owned data and record role transitions and local alerts.
4. **Measure partition tradeoffs.** Separately remove Sentinel quorum and introduce a reversible, scoped network partition. Observe both old/new primary views, write rejection, client discovery, and convergence after healing. Record acknowledged, failed, timed-out/ambiguous, lost, and duplicate outcomes where measurable; aggregate counts alone cannot prove exact operation identity. Use uniquely named store operations and counter observations together, retaining ambiguity rather than guessing. Explain non-replayable WebSocket gaps and reconnection behavior. Rehearse issue 41's backup/restore in Sentinel mode before claiming that coverage.

**Exit evidence:** repeated failure timelines and honest availability/data-integrity results. Asynchronous replication can lose acknowledged writes; do not assert universal counter monotonicity, exact-once increments, fencing, or split-brain immunity. All workers still share one host. Use `feat(redis)` and `test(failover)` commits and keep this opt-in.

## Issue 41 Backup and fresh cluster restore

[Issue 41](https://github.com/kajuyerim/docker-based-multiserver-system/issues/41). **Entry:** issues 34, 36, and 37. **Prepare:** snapshot consistency, recovery point objective (acceptable data loss), and recovery time objective (time to restored service). **Targets:** backup/restore helpers, backup metadata schema, explicit schedule instructions, and `docs/runbooks/restore.md`.

1. **Define the snapshot and retention contract.** Choose a Redis-supported completed RDB snapshot/export procedure compatible with the pinned Redis version; never copy a live AOF file as a complete backup. Record snapshot start/boundary/completion, source release and Redis version, data identity, hashes, and restore compatibility. Keep backups in an owned host directory outside kind and source volumes with explicit permissions, encryption/key handling, and retention. Decide RPO/RTO targets and whether the drill includes cold downloads. [Redis persistence and backup guidance](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).
2. **Implement safe backup and failure checks.** Produce an on-demand snapshot, wait for successful completion, copy/export it, verify its checksum, and publish its metadata atomically. Use bounded timeouts, prevent overlapping jobs, and keep incomplete output distinct. Document a local schedule that is disabled until explicitly enabled; define missed runs and host-off behavior. Test permission failures, interrupted output, corruption, and incompatible metadata/version rejection. Retention acts only on recognized owned backup sets.
3. **Restore without the original data.** Seed uniquely identifiable fixtures/counters, quiesce or precisely mark the snapshot boundary, and record later writes separately. Create a differently named isolated cluster and fresh volume with no mounts/network access to the source data. Recreate infrastructure and GitOps/secrets from documented inputs. Restore before ordinary app traffic, coordinating Flux reconciliation so it cannot start an empty writable service mid-restore. Explicitly handle AOF precedence: load the snapshot with a version-tested procedure, establish AOF from restored data, and prove a restart retains it before reopening traffic.
4. **Measure complete recovery.** Validate fixture values and the restored counter directly before smoke tests increment it, then check replica synchronization, authentication, API, and restart persistence. Measure actual lost accepted writes and end-to-end RTO including cluster recreation. Prove routine teardown retains backups and explicit deletion affects only owned data. Document an optional second-device copy; same-laptop storage does not protect against laptop/disk loss. Add current-primary discovery and a new restore rehearsal when Sentinel mode arrives.

**Exit evidence:** checksummed external backup, fresh-cluster restore transcript, measured RPO/RTO, negative tests, and a usable recovery runbook. No scheduler is enabled as part of planning. Use `feat(backup)` and `test(restore)` commits; decide storage/key location and retention in phase 1.

## Issue 42 Operations game day and case study

[Issue 42](https://github.com/kajuyerim/docker-based-multiserver-system/issues/42). **Entry:** issues 32–39 and 41. Issue 40 and the simulator are optional later additions. **Prepare:** explain one operational story through evidence rather than a tool inventory. **Targets:** `docs/case-study.md`, a game-day guide, sanitized evidence/screenshots, a static shareable artifact, and a README entry point.

1. **Script the five-minute story.** Start with an already prepared lab, verify a release, promote its digest through Flux, induce a controlled failure, observe the local alert, use a runbook, and validate recovery/rollback. Include preparation and cleanup instructions with their real durations separately; do not hide them in a five-minute reproducibility claim. Choose a failure that can trigger the declared alert. Provide the fresh-cluster restore as a separate exercise using issue 41.
2. **Record fresh measured evidence.** Run only against disposable, explicitly owned resources. Capture source revision, image/config digests, topology, workload, timestamps, declared thresholds, raw results, resource/hardware limits, and cleanup. Build a compact release/recovery/scaling results table from these records, with direct evidence links. Distinguish an edited walkthrough from the full measured recovery time.
3. **Explain the incident and decisions.** Write one concise postmortem with impact, detection, timeline, root cause, recovery, and specific follow-ups grounded in the actual drill. Add an architecture/ownership diagram, screenshots or a short local recording, and decisions on OpenTofu versus Flux, single-host limits, primary failover versus backup, and deferred heavier tools. Describe a local Kubernetes platform, not a deployed production cloud service.
4. **Prepare a reviewable public export.** Audit the intended tracked files, relevant history, and evidence for secrets/personal academic information. Preserve both authors' credit and record the license decision with them. Produce a sanitized static HTML or PDF case-study artifact that can be shared without paid hosting; do not change repository visibility. Add the README entry point. Link the simulator if already available, and append separately labeled Sentinel evidence once issue 40 is delivered.

**Exit evidence:** a reproducible initial walkthrough, separate restore exercise, postmortem, measured results table, and reviewed static artifact. Publish the initial case study without waiting for Sentinel. Treat the later Sentinel evidence as a tracked follow-up; if the issue remains open for that conditional criterion, distinguish that from the first version being delivered. Use `docs(portfolio)` phase commits.
