# v1.1 Reproducible and secure delivery plans

This milestone creates trustworthy build inputs, verifiable release outputs, and a bounded local environment. Issue 32 depends on 31. Issue 33 can start independently; both 32 and 33 feed GitOps in issue 34. Follow the [shared phase and evidence workflow](README.md).

## Issue 31 CI trust and dependency maintenance

[Issue 31](https://github.com/kajuyerim/docker-based-multiserver-system/issues/31). **Entry:** completed v0.5. **Prepare:** workflow events, token permissions, action pinning, and what untrusted PR code can execute. **Targets:** `.github/workflows/ci.yml`, `.github/dependabot.yml`, a local CI-validation script, synthetic fixtures, and `docs/ci-security.md`.

1. **Inventory and restrict trust.** Map triggers, checkout refs, permissions, secret access, artifacts/caches, and runner types. Set read-only contents permission by default. Keep contributed-code checks on disposable runners without publishing/signing privileges; do not add privileged PR triggers or a persistent laptop runner. Account for trusted workflows that later consume artifacts from untrusted runs. Review the resulting boundary against [GitHub's secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use).
2. **Verify dependencies and downloads.** Resolve each action tag to a reviewed full commit SHA with a readable version annotation. Verify downloaded kind/Helm/tool artifacts against trusted pinned checksums or signatures before execution. Document where those expectations came from and how to update them. Add one updater, proposed Dependabot, covering Go, Docker images, and Actions; include simulator npm after that workspace exists. Group compatible updates, bound concurrent PRs, and leave automatic merging disabled.
3. **Add focused local checks.** Use pinned [actionlint](https://github.com/rhysd/actionlint) for workflow syntax/semantics and [Gitleaks](https://github.com/gitleaks/gitleaks) for secrets, with a small explicit policy check where the linter does not enforce permissions, SHA pins, or unsafe triggers. Exercise safe and deliberately unsafe workflow fixtures and clearly synthetic credentials in temporary fixtures. A failed download-integrity fixture must stop before execution. Avoid broad exclusions that make the negative tests meaningless.
4. **Prove the maintenance workflow.** Run existing acceptance gates plus the new checks, then carry one representative dependency update through normal review and tests. Verify the upstream change and regenerated locks; retain the diff and results. Document local equivalents so hosted Actions minutes are optional for doing the checks. If updater delivery is delayed, a manually prepared representative update can exercise the review process, with its origin stated accurately.

**Exit evidence:** trust-boundary document, rejected unsafe fixtures, preserved baseline gates, and one reviewed update. This issue improves orchestration trust; existing vulnerability scanners remain in place without adding a duplicate scanner.

**Decision before phase 2:** agree the update cadence/grouping. Proposed default: weekly updates, compatible patch/minor groups, and a small open-PR cap; security fixes remain separately reviewable. Use `ci(security)` and `chore(deps)` phase commits.

## Issue 32 Verifiable OCI releases

[Issue 32](https://github.com/kajuyerim/docker-based-multiserver-system/issues/32). **Entry:** issue 31. **Prepare:** image tags versus immutable digests, SBOMs, provenance, and signer identity. **Targets:** release scripts and manifest schema, Helm image values/template, release documentation, and an optional trusted release workflow.

1. **Specify a local release.** Choose a local OCI registry as the default installation path, reachable by the owned kind lab, with a protected local signing key outside the repository. Define a release manifest with source revision, image repository/digest/platform, Helm package version/hash, tool versions, build inputs, and validation results. Record only architectures actually built and tested. Separate building unsigned output from the trusted signing decision; refuse an unexplained dirty source tree.
2. **Produce and verify artifacts.** Build once, package the chart, generate an SPDX or CycloneDX SBOM, and create signed provenance whose subject is the image digest. Bind chart and SBOM hashes through the signed release metadata as well. Use a documented pinned public-key trust root and local [Cosign self-managed keys](https://docs.sigstore.dev/cosign/key_management/signing_with_self-managed_keys/); explicitly configure the local verification path without requiring a public transparency-log upload. Document key creation, restricted storage, backup, and rotation, and explain that a local signature does not establish a hosted builder identity.
3. **Deploy the verified digest.** Add `image.digest` support with digest precedence and a compatible tag fallback for the existing simple demo. Validate values and render both paths; regenerate the checked-in default manifests if affected. Pull/install exactly the verified digest without rebuilding between verification and deployment. Run API, auth, and cross-replica WebSocket checks on it.
4. **Exercise rejection and rollback.** Reject changed image content, wrong signer, mismatched provenance subject/revision, and altered chart/SBOM metadata. Install release A, promote tested B, then restore A by digest in a disposable lab. Capture release metadata, actual container image IDs, API outcomes, and rollback results. Keep remote publishing separately opt-in and within free allowances.

**Exit evidence:** two identifiable releases, SBOM and signed provenance, successful and failed verification transcripts, and exact-digest install/rollback. An OCI archive is an optional alternative, not a second mandatory transport. Check compatibility with the pinned tooling before promising archive-based digest installation.

**Decision before phase 1:** select the registry name, local trust-key location, version convention, and tested platform. Use `feat(release)` phase commits. Do not publish private source metadata externally as a side effect of signing.

## Issue 33 Reproducible OpenTofu lab

[Issue 33](https://github.com/kajuyerim/docker-based-multiserver-system/issues/33). **Entry:** completed v0.5. **Prepare:** OpenTofu plans/state and Kubernetes resource ownership. **Targets:** `infra/local/`, separate kind lab profiles, lifecycle/preflight helpers, dependency locks, and `docs/local-platform.md`.

1. **Define ownership and budget.** Keep `scripts/deploy-kind.sh` as the simple deployment. Design a new named lab with a small default and an opt-in multi-worker profile. Proposed bootstrap ownership: OpenTofu owns platform namespaces, ingress, metrics-server, Flux installation, and later the CNI installation; Flux owns application releases, policies, and selected telemetry add-ons. HPA owns application replica counts. Record that table before creating resources, including who owns CRDs and storage. Choose a free runtime path for Apple Silicon and Linux; measure the tested budget rather than inventing a minimum.
2. **Build the declarative bootstrap.** Keep kind creation in a thin lifecycle helper, without shell provisioners hidden in OpenTofu. Use Kubernetes/Helm providers for meaningful bootstrap resources, pinned tools/charts/providers, and committed dependency locks for supported platforms. Create the cluster before provider initialization against its API. Stage CRDs/controllers before resources that require them; prepare the profile interface for issue 35's CNI choice. Test format/validation and a fresh plan.
3. **Demonstrate state and drift.** Apply, require a second plan with no changes, introduce a harmless bootstrap drift, and show its correction. Explain refresh/plan/apply using the actual evidence. Keep state, sensitive plan output, kubeconfigs, and credentials outside Git; document local locking and recovery without claiming remote team coordination. [OpenTofu state concepts](https://opentofu.org/docs/language/state/).
4. **Recreate and measure safely.** Record CPU, memory, disk, startup time, and resource limits for the default profile; opt into the larger profile and repeat its preflight. Destroy/recreate only the named lab and show the same intended topology returns. Distinguish stopping containers, removing the cluster, and deleting retained data. Require an explicit destructive data action for owned persistent storage and preserve unrelated volumes. Remove managed resources while the API still exists, then remove kind; document recovery if the cluster was already lost.

**Exit evidence:** reviewed plans, zero-change reapply, corrected drift, resource measurements, and clean recreation. Cluster deletion is not a backup strategy; issue 41 later proves recovery from external snapshots.

**Decision before phase 1:** agree CPU/memory/disk ceilings, cluster/namespace prefixes, and state directory. A candidate multi-worker topology is one control-plane node plus three workers; only make it supported after measurements. Use `feat(infra)` phase commits.
